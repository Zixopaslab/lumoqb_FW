Lumoqb internet radio: architecture

How a station gets from the phone app, through Wi-Fi and the MP3 decoder, to the speaker and the six cube faces. Built from the firmware in 02_FW and the app in 03_App.

The short version

Each of the cube's six sides is a radio slot. Turn a side up and hold it for 750 ms, and the firmware opens a plain HTTP connection to that slot's MP3 stream, buffers it, decodes it with the Helix library and plays it through I2S. A live 8-band spectrum, computed from the decoded audio, draws the equalizer on the face (or drives the ferrofluid visual). There is no HTTPS, no HLS, no AAC and no ICY metadata. The stream must be a direct MP3 stream, because the ESP32 has no PSRAM.

2. Configuring a station

Built-in catalog

RADIO_CATALOG[12] in main.cpp holds 12 direct 128 kbps MP3 endpoints (ten SomaFM channels, Radio Parsa, Radio Hamrah). The saved faceSettings.radio[side] index picks one per side at boot (applyFaceCatalogs()).

Custom world stations

In the app, users search radio-browser.info and pick a station. radioRecord() rejects anything that is not MP3, is HLS, is HTTPS, is over 192 kbps, is a .m3u/.pls playlist, or has an address that is too long. The firmware validates the record again (worldRecord(): ASCII only, host charset, port 1–65535, path starts with /) before it saves it to NVS.

BLE hand-off

The BLE callback only copies a bounded command into a mutex-guarded slot. The main loop owns NVS writes, audio shutdown and redraws, so BLE can never touch the audio path directly. If a stream is playing when a side's station changes, the main loop stops it first.

3. Connecting: startRadioStation()

  1. Free the speaker. Stop any continuous Lumo microphone capture (stopContinuousLumoCaptureForPlayback). The dashboard also closes SD voice and the focus alarm so I2S is free.
  2. Tear down the old stream (stopRadioStream()): disable the visualizer, set audio_stop_requested, wait up to 1 s for the task to exit (force-delete it if it does not), close the socket, free the decoder and ring buffer, zero the DMA buffers.
  3. Join Wi-Fi. WiFi.mode(STA), then autoConnectSavedWifi() if not already connected. If it fails, the face shows WIFI FAILED. Modem sleep stays on, because the Wi-Fi/BLE coexistence build aborts without it.
  4. Open TCP and send a minimal request. GET path HTTP/1.0, Accept: audio/mpeg, Icy-MetaData: 0, Connection: close. HTTP/1.0 is used on purpose so the server will not use chunked encoding.
  5. Parse headers by hand (readRadioHeaderLine(), 8 s budget, 1 KB line cap, 64 headers max). The firmware accepts 200. It follows 301/302/307/308 up to 3 times, using Location: as either an absolute http:// URL or a path.
  6. Refuse unsupported framing. A chunked response, or an icy-metaint > 0 header, aborts the connection. Either would put non-audio bytes in the MP3 stream.
  7. Start playback. Allocate the 8 KB ring (RadioBufferedStream::begin), allocate the Helix decoder (beginChecked(), which uses nothrow allocation), start the MP3 task, enable the visualizer and set the face to PLAYING.

Every failure path sets radioLastStartAttemptMs and shows RETRYING or an error. The main loop retries (section 6).

4. Two tasks, one lock-free hand-off

Shared state between the two tasks is only std::atomic values (radioVizLevels, radioVizRmsQ15, radioVizUpdated, radioVizEnabled) and the volatile audio_stop_requested flag. There are no mutexes or queues between them, and the visualizer never copies PCM data.

5. Buffering and the audio path

RadioBufferedStream src/radio_buffer.h

An 8,192-byte ring that sits between the socket and Helix. It is a Stream subclass, so the decoder task reads it like any stream. It has no task of its own: the decoder task calls fill() from inside available() and readBytes().

  • Prefill: the first read waits for 4,096 bytes (up to 5 s).
  • Underrun: if the ring empties, it waits for just 1 byte, not another full prefill, to keep the gap short. It then logs the underrun count, heap and largest free block.
  • Dead socket: an empty read does a MSG_PEEK on the socket to log whether the peer closed it.
  • Stop: every wait loop checks audio_stop_requested.

Decode and output src/esp32_audio_task.h

  • Decoder: Helix MP3 via a PixyToyMP3DecoderHelix subclass. Its PCM buffer is trimmed from 5,120 to 2,305 samples (one max stereo frame plus a guard sample), which frees heap for Wi-Fi and BLE.
  • Sample rate: the first frame sets the I2S clock with i2s_set_clk() (rate and mono/stereo from the stream).
  • Volume: scales samples by the 0–100 % setting. Alert mode other than 2 forces volume to 0.
  • I2S: port 0, 16-bit, 8 DMA buffers × 160 frames. writeAudioFully() aborts the stream if no sample is accepted for 500 ms.

6. Failure handling and reconnect

ConditionWhat the firmware does
Socket read times out (5 s) or server closesThe MP3 task exits and sets mp3TaskHandle = NULL. updateRadioMode() sees that, waits until RADIO_RETRY_INTERVAL_MS (5 s) has passed since the last attempt, then calls startRadioStation() again.
Wi-Fi dropsThe main loop sees WiFi.status() != WL_CONNECTED, stops the stream, and reconnects through the same retry path.
Network stall (no data, socket alive)The buffer starves, logs an underrun, and resumes on the first new byte. The code intentionally does not use the I2S timestamp to detect stalls, because that caused false reconnects.
I2S output stalls > 500 ms, or decoder makes no progressSets audio_stop_requested; the task exits and the reconnect path runs.
Not enough heap for ring buffer or decoderLogs the free and largest block, shows AUDIO ERROR or retries later. It does not reboot.
Bad response (not 200, 4 redirects, chunked/ICY metadata, bad headers)Closes the socket, shows RETRYING, retries after the interval.
Stop requested but task is stuckstopRadioStream() waits 1 s, then force-deletes the task with Stop_Audio_Tasks().

While a stream is playing, background HTTPS refreshes (weather, stocks, clock sync) are skipped: mp3TaskHandle != nullptr || radioStreamClient.connected() blocks them. The decoder and TLS both need a large contiguous heap block that the ESP32 does not have for both at once.

7. Visualizer pipeline

Data counts as "fresh" only if the last analysis is under 500 ms old. When it goes stale (paused, rebuffering), the bars decay to zero rather than freezing. Ferrofluid style is selectable per source (0 equalizer, 1 black, 2 full color, 3 localized color bands) with the audio_visual_set BLE message, and saved in the audio_visual NVS namespace. ferroRadioBegin() reuses updateRadioMode() for station choice and reconnects, so the ferrofluid mode needs no separate streaming code.

8. Limits to know about

  • HTTP only. No TLS on the stream. HTTPS stations are filtered out in the app, and the firmware cannot follow an https:// redirect.
  • MP3 only in practice. The AAC decoder is compiled in and has a task starter, but startRadioStation() only ever starts the MP3 task, and the request sends Accept: audio/mpeg.
  • No metadata. Titles shown on the faces come from the catalog or the user's saved name, not from the stream.
  • One stream at a time. Changing side tears the old one down fully before the new one opens, which causes a brief gap.
  • Memory-driven design. No PSRAM; the 8 KB ring, 2,305-sample PCM buffer, trimmed BLE config and no-FFT visualizer all exist to keep a large heap block free.
